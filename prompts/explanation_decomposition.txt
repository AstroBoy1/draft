You are a chess-explanation decomposition system.

Given a starting FEN and a free-form chess explanation, decompose the explanation into ordered atomic claims.
The explanation is in the final_explanation_summary.

## Input

FEN:

```text
{FEN}
```

Explanation:

```text
{EXPLANATION}
```

## Output

Return only valid JSON using this structure:

```json
{
  "fen": "string",
  "claims": [
    {
      "id": 0,
      "parent_id": null,
      "text": "string",
      "atomic_claim": "string",
      "moves": ["uci_string"],
      "pieces": ["piece_string"],
      "squares": ["square_string"],
      "evaluation": "white_better",
      "concept": {
        "category": "tactical_motif",
        "name": "string"
      },
      "relation_to_parent": null
    }
  ]
}
```

Each claim must follow these types:

```text
id: integer
parent_id: integer | null
text: string
atomic_claim: string
moves: array of UCI strings | null
pieces: array of piece strings | null
squares: array of square strings | null
evaluation: "white_better" | "equal" | "black_better" | null
concept: object | null
relation_to_parent: "support" | "refute" | null
```

## Rules

1. Split the explanation into independently verifiable atomic claims.

2. Preserve claim order. Set each `id` to its zero-based index in the `claims` array.

3. `text` must be the complete original sentence containing the claim, preserved exactly. Repeat the sentence when it contains multiple claims.

4. `atomic_claim` must be the complete sentence or an exact contiguous substring of `text`. Do not paraphrase or correct it.

5. Preserve incorrect or illegal claims as written. Do not evaluate their correctness.

6. `parent_id` identifies the earlier claim most directly supported or refuted by the current claim:

   - `"support"`: the current claim provides a reason, explanation, evidence, or consequence supporting the parent.
   - `"refute"`: the current claim contradicts or invalidates the parent.
   - Use `null` for both fields when no clear relationship exists.
   - A parent must have a smaller `id`.

7. `moves` contains only moves referenced by the atomic claim:

   - Convert moves to UCI using the FEN and variation context.
   - Preserve move order.
   - Use `null` when no move is referenced or the UCI move is ambiguous.
   - Do not infer unmentioned moves.

8. `pieces` contains relevant pieces using only:

```text
white_king, white_queen, white_rook, white_bishop, white_knight, white_pawn,
black_king, black_queen, black_rook, black_bishop, black_knight, black_pawn
```

Use `null` when no particular piece is relevant.

9. `squares` contains relevant lowercase squares from `a1` through `h8`, including move origins and destinations when known. Use `null` when none are relevant.

10. `evaluation` records an evaluation explicitly stated or directly entailed by the atomic claim:

- White is better or winning → `"white_better"`
- Equal or balanced → `"equal"`
- Black is better or winning → `"black_better"`
- Otherwise → `null`

Do not infer an evaluation merely because a good move, threat, or tactic is mentioned.

11. `concept` identifies at most one primary chess concept:

```json
{
  "category": "tactical_motif | strategic_concept",
  "name": "lowercase_snake_case"
}
```

Use `"tactical_motif"` for immediate tactical patterns and `"strategic_concept"` for positional or long-term ideas. Use `null` when no concept is clearly expressed.

12. Every claim object must contain every key. Use JSON `null`, never `"null"`. Do not add extra keys, Markdown, or commentary.
